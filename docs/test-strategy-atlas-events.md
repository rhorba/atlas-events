## 2. Test Pyramid Targets

### atlas-api (Spring Boot 3 / Java 21)

| Layer | Target | Tooling |
|---|---|---|
| Unit | ≥ 65% of domain + application layer | JUnit 5, Mockito — no Spring context |
| Integration | ≥ 40% of infra layer (controllers, repos, consumers) | `@SpringBootTest` + Testcontainers (PostgreSQL 16, RabbitMQ 3) |
| **Combined gate** | **≥ 80%** — CI blocks merge if below | JaCoCo; Maven Surefire + Failsafe |

Coverage measured by JaCoCo; report generated by `mvn verify`. Excludes: generated code, DTOs, config classes.

### atlas-scraper (Spring Batch / Java 21)

| Layer | Target | Tooling |
|---|---|---|
| Unit | ≥ 70% of scraper logic (reader/processor/writer) | JUnit 5, Mockito, fixture HTML files |
| Integration | ≥ 40% of batch job execution | Spring Batch Test (`JobLauncherTestUtils`), Testcontainers (RabbitMQ) |
| **Combined gate** | **≥ 80%** | JaCoCo |

Each scraper tested with real fixture HTML snapshots (stored in `src/test/resources/fixtures/`). Prevents silent breakage when source sites change structure.

### atlas-web (Angular 17)

| Layer | Target | Tooling |
|---|---|---|
| Unit | ≥ 60% of components + services | Jest + Angular Testing Library (`@testing-library/angular`) |
| Integration | Key service + HTTP layer | Jest + `HttpClientTestingModule` |
| E2E | Critical happy paths only | Playwright (`@playwright/test`) |
| **Combined gate** | **≥ 80%** | Istanbul (Jest coverage); `ng test --coverage` |

## 3. ATDD Acceptance Scenarios

### Feature: Event Discovery

```gherkin
Feature: Attendee browses events

  Scenario: Default view shows upcoming events across all cities
    Given the database contains 10 approved upcoming events across 5 cities
    When a visitor loads the event list with no filters
    Then all 10 events are returned ordered by start_date ascending
    And deleted events are not included

  Scenario: Filter by city returns only matching events
    Given events exist in Casablanca (3) and Rabat (2)
    When a visitor filters by city "casablanca"
    Then only the 3 Casablanca events are returned

  Scenario: Filter by date range "this_week"
    Given today is 2026-07-01
    And there are events on 2026-07-03, 2026-07-10, and 2026-08-01
    When a visitor filters by range "week"
    Then only the 2026-07-03 event is returned

  Scenario: Empty result returns empty list, not an error
    Given no events exist for city "tangier" and category "workshop"
    When a visitor filters by city "tangier" and category "workshop"
    Then the response status is 200
    And the events array is empty
```

### Feature: iCal Feed

```gherkin
Feature: iCal subscription

  Scenario: Feed returns valid iCal for filtered events
    Given 3 approved upcoming events exist in Casablanca
    When a calendar app subscribes to GET /ical?city=casablanca
    Then the response Content-Type is "text/calendar"
    And the response contains 3 VEVENT entries
    And each VEVENT has DTSTART in timezone "Africa/Casablanca"

  Scenario: Empty filter returns all upcoming events
    Given 5 approved upcoming events exist across all cities
    When a client calls GET /ical with no parameters
    Then the response contains 5 VEVENT entries
```

### Feature: Community Submission

```gherkin
Feature: Event organiser submits an event

  Scenario: Valid submission is accepted and stored as pending
    Given a valid submission payload (title, start_date, city, organiser, category, registration_url)
    When POST /api/v1/submissions is called
    Then the response status is 201
    And the submission is stored with status "pending"
    And contact_email is not present in the response body

  Scenario: Submission with missing required field is rejected
    Given a submission payload with no title_fr
    When POST /api/v1/submissions is called
    Then the response status is 400
    And the response body contains a validation error for "titleFr"

  Scenario: Submission rate limit is enforced
    Given the same IP has submitted 10 events within the last hour
    When an 11th submission is attempted from the same IP
    Then the response status is 429
    And the retry-after header is present
```

### Feature: Admin Authentication

```gherkin
Feature: Admin login and JWT

  Scenario: Valid credentials return a JWT
    Given admin credentials are configured in environment variables
    When POST /api/v1/auth/login is called with correct username and password
    Then the response status is 200
    And the response body contains a "token" field
    And the token is a valid JWT with issuer "atlas-events" and 1-hour expiry

  Scenario: Invalid credentials return 401 without revealing which field was wrong
    When POST /api/v1/auth/login is called with wrong password
    Then the response status is 401
    And the response body contains "Invalid credentials"
    And the response does not reveal whether the username or password was wrong

  Scenario: Protected endpoint returns 401 without JWT
    When GET /api/v1/admin/submissions is called without Authorization header
    Then the response status is 401

  Scenario: Protected endpoint returns 401 with expired JWT
    Given a JWT that expired 1 hour ago
    When GET /api/v1/admin/submissions is called with that token
    Then the response status is 401

  Scenario: Login lockout after 10 consecutive failures
    Given 9 failed login attempts from IP "1.2.3.4"
    When a 10th failed attempt occurs from the same IP
    Then the response status is 429
    And the account is locked for 15 minutes
```

### Feature: Admin Submission Moderation

```gherkin
Feature: Admin moderates community submissions

  Scenario: Admin approves a pending submission — event appears publicly
    Given a submission with status "pending" exists (id: "sub-123")
    And admin is authenticated with a valid JWT
    When POST /api/v1/admin/submissions/sub-123/approve is called
    Then the submission status becomes "approved"
    And a corresponding event is created in the events table with status "upcoming"
    And the event is returned in the public event list

  Scenario: Admin rejects a submission with a note
    Given a submission with status "pending" exists (id: "sub-456")
    When POST /api/v1/admin/submissions/sub-456/reject is called with body { "note": "Off-topic" }
    Then the submission status becomes "rejected"
    And reviewNote is "Off-topic"
    And no event is created in the events table

  Scenario: Double-approve is idempotent
    Given a submission with status "approved" exists (id: "sub-789")
    When POST /api/v1/admin/submissions/sub-789/approve is called again
    Then the response status is 409 or 200 (idempotent)
    And no duplicate event is created
```

### Feature: Scraper Deduplication Pipeline

```gherkin
Feature: RabbitMQ scrape pipeline and deduplication

  Scenario: New scraped event is persisted
    Given the events table is empty
    When atlas-scraper publishes a ScrapedEvent message to the "events.scraped" queue
    And atlas-api consumes the message
    Then the event is inserted into the events table with status "upcoming"

  Scenario: Duplicate scraped event is silently skipped
    Given an event with source_url="https://10times.com/e1", title_fr="Summit X", start_date="2026-08-01" already exists
    When atlas-scraper publishes a second message with the same (source_url, title_fr, start_date)
    And atlas-api consumes the message
    Then no duplicate row is inserted
    And no error is thrown — the operation is a silent no-op

  Scenario: Malformed message is routed to dead-letter queue
    When atlas-scraper publishes a message with missing required field "title"
    And atlas-api fails to process it after 3 retries
    Then the message is routed to the "events.dead" dead-letter queue
    And an error is logged with the message ID and failure reason
```

## 4. Adversarial Checklist

### Tier 1 — Maximum Risk Components

**JWT Admin Auth**
- [ ] Access `/api/v1/admin/**` with no token → expect 401
- [ ] Access with expired token (1 second past expiry) → expect 401
- [ ] Access with token signed by a different secret → expect 401
- [ ] Access with JWT `alg: none` attack → expect 401
- [ ] Brute-force login (>10 attempts) → expect 429 + lockout
- [ ] JWT issued for wrong issuer claim → expect 401

**Scraper HTML Parsing**
- [ ] Empty HTTP response body → graceful skip, no exception
- [ ] HTML with 0 matching events → returns empty list, no error
- [ ] HTML with malformed date strings → event skipped, error logged
- [ ] HTTP 429 (rate-limited by source) → retry with backoff, not crash
- [ ] HTTP 500 from source site → scraper marks job failed, logs error, does not crash pipeline
- [ ] `robots.txt` disallows the path → scraper skips, logs "disallowed by robots.txt"

**RabbitMQ Pipeline**
- [ ] RabbitMQ down when scraper tries to publish → scraper job fails gracefully, logged
- [ ] Message with null `start_date` consumed by atlas-api → validation rejects, routes to DLQ
- [ ] 1000 duplicate messages published simultaneously → only 1 event inserted (unique constraint holds)
- [ ] Consumer crashes mid-batch → messages requeued by RabbitMQ, reprocessed on restart

**Deduplication**
- [ ] Two concurrent threads insert same event → only 1 inserted (PostgreSQL unique constraint + ON CONFLICT DO NOTHING)
- [ ] Same event with different whitespace in title → treated as duplicate (normalise before hash)
- [ ] Same event with different capitalisation → treated as duplicate (case-insensitive compare at app layer)

### Tier 2 — High Risk Components

**Submission Form / API**
- [ ] `title_fr` with 10 000-character string → 400 validation error
- [ ] XSS in `title_fr`: `<script>alert(1)</script>` → stored as plain text, rendered escaped in Angular
- [ ] SQL injection in `organiser` field → ORM parameterisation prevents execution
- [ ] `registration_url` with `javascript:alert(1)` → 400 validation error (URL format check)
- [ ] `category` value not in enum → 400 validation error
- [ ] `city` value not in allowed list → 400 validation error
- [ ] `contact_email` appears in GET `/api/v1/admin/submissions` response → must be absent (`@JsonIgnore`)

**Event List API**
- [ ] `page=-1` → treated as page 0 or 400
- [ ] `size=999999` → capped at max page size (e.g. 50)
- [ ] Unknown `city` value in filter → 0 results, no error
- [ ] Unknown `category` value in filter → 0 results or 400

## 7. Release Gate Criteria

Before any SHIP phase, all of the following must be green:

- [ ] **Coverage**: Combined unit + integration ≥ 80% on all three modules (atlas-api, atlas-scraper, atlas-web). JaCoCo / Istanbul reports in CI.
- [ ] **All ATDD scenarios pass**: Every Gherkin scenario from Section 3 has a passing automated test.
- [ ] **Adversarial Tier 1 complete**: All Tier 1 items checked and passing.
- [ ] **No open Critical or High bugs**: Zero unresolved findings in `.logs/issues.md` at severity Critical or High.
- [ ] **Security scan clean**: Trivy finds no Critical CVEs; Semgrep finds no High SAST findings.
- [ ] **E2E smoke suite green on staging**: Playwright suite passes on the staging K8s environment.
- [ ] **Load test baseline met**: p99 < 500ms for event list at 50 concurrent users.
- [ ] **WCAG axe-core clean**: Zero violations on event list, event detail, and submit form pages.
